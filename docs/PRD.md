# PRD: Niko Admin - 基于 Gin + React Admin 的后台管理系统脚手架

---

## 1. Executive Summary

**Problem**: 团队每次启动新后台项目都需要重复搭建认证、权限、日志、文件管理等基础设施，缺乏统一可复用的 Go 后端脚手架，导致开发效率低下、各项目风格不一致。

**Solution**: 开发一套基于 Gin + GORM + PostgreSQL + Redis 的后端脚手架，配合 React Admin 开源前端，提供开箱即用的后台管理系统模板，覆盖认证、RBAC、审计日志、文件管理、WebSocket 实时推送、异步任务队列等核心能力。

**Success Criteria**:

| # | KPI | Target |
|---|-----|--------|
| 1 | 新项目从 0 到 API 联调完成 | <= 30 分钟 |
| 2 | CRUD API 代码生成 | 1 个 Model 从定义到 API 就绪 <= 5 分钟 |
| 3 | API 响应时间 (P99) | <= 100ms (排除网络延迟) |
| 4 | RBAC 权限验证性能 | <= 5ms/次 (Redis 缓存命中时) |
| 5 | 系统测试覆盖率 | >= 70% |

## 2. User Experience & Functionality

### 2.1 User Personas

| Persona | Role | Needs |
|---------|------|-------|
| **后端开发者** | 使用脚手架开发新项目 | 快速生成 CRUD、了解项目结构、易扩展 |
| **前端开发者** | 对接 React Admin 与后端 API | 遵循标准的 RESTful 规范、清晰的 API 文档 |
| **系统管理员** | 管理后台用户和权限 | 直观的权限分配、操作审计追踪 |

### 2.2 User Stories

#### Story 1: 项目初始化
- **As a** 后端开发者
- **I want to** 通过命令快速创建一个新后台项目
- **So that** 我不需要从零搭建项目结构

**Acceptance Criteria**:
- 提供 CLI 命令或脚本完成项目初始化
- 初始化后项目可直接 `go run` 启动
- 默认包含完整的项目目录结构
- 提供 `docker-compose.yml` 一键启动依赖服务（PostgreSQL + Redis）

#### Story 2: 用户认证
- **As a** 系统管理员
- **I want to** 使用用户名/密码登录系统
- **So that** 我可以安全地访问后台管理功能

**Acceptance Criteria**:
- 支持用户名 + 密码登录
- 登录成功后返回 access_token（2h）和 refresh_token（7d），双 Token 机制
- Access Token：
  - JWT 短时效（默认 2h），承载用户 ID、角色 ID 列表
  - 每次请求通过 `Authorization: Bearer <token>` 携带
  - 无状态验证，不查 Redis，降低 RT
- Refresh Token：
  - 随机生成的 UUID 字符串（非 JWT），存储在 Redis：`refresh:{user_id}:{token_id}` → `{user_id, expires_at, device}`
  - 通过 httpOnly + Secure + SameSite=Strict Cookie 传递（前端 JS 不可访问，防 XSS）
  - 刷新时：旧 refresh_token 立即失效，签发新的 access_token + refresh_token（滚动刷新策略 Rotation）
  - **复用检测**：若已被撤销的 refresh_token 被再次使用（疑似泄露），立即撤销该用户所有 refresh_token，强制重新登录
- Token 退出登录时，access_token 加入 Redis 黑名单（TTL = 剩余有效期），refresh_token 同步删除
- 登录失败连续 5 次锁定账号 15 分钟
- 密码使用 bcrypt（cost=12）加密存储
- 支持 `POST /auth/refresh` 无感刷新，React Admin 的 authProvider 自动拦截 401 调用此接口

#### Story 3: RBAC 权限管理
- **As a** 系统管理员
- **I want to** 创建角色并为角色分配菜单/API 权限
- **So that** 不同用户只能访问授权范围内的功能

**Acceptance Criteria**:
- 支持用户管理（创建、编辑、禁用、删除）
- 支持角色管理（创建、编辑、删除）
- 支持资源/权限点管理（API 路径 + HTTP 方法）
- 支持角色 ⇔ 用户的多对多关联
- 支持角色 ⇔ 权限的多对多关联
- 权限验证在 Gin 中间件层实现
- 权限变更后支持动态刷新（无需重启服务）
- Redis 缓存角色权限，设置 5 分钟 TTL

#### Story 4: CRUD 代码生成
- **As a** 后端开发者
- **I want to** 通过定义 Model 结构体自动生成 CRUD API
- **So that** 减少重复 boilerplate 代码编写

**Acceptance Criteria**:
- 根据 GORM Model 定义生成标准 CRUD 接口（Create/Read/Update/Delete/List）
- 生成代码包含：Handler、Service、Repository、Router、DTO（请求/响应结构体）
- 生成的 Handler 中自动包含 Swagger 注解（`@Summary`、`@Param`、`@Success`、`@Router`）
- List 接口支持分页、排序、模糊搜索（根据 string 字段自动生成搜索条件）
- 代码生成器需可配置输出路径和包名
- 生成的代码遵循项目统一的错误处理规范和分层架构
- 生成的文件带有 `// Code generated by niko-admin. DO NOT EDIT.` 头部标记
- 支持 `-f` 参数指定单个 Model 文件生成，或 `--all` 批量生成所有 Model

#### Story 5: 审计日志
- **As a** 系统管理员
- **I want to** 查看所有用户的操作记录
- **So that** 我可以追踪安全事件和责任归属

**Acceptance Criteria**:
- 自动记录所有对数据库的写操作（Create/Update/Delete）
- 记录内容包括：操作用户、操作时间、操作类型、请求 IP、请求路径、请求参数、影响数据
- 审计日志不可删除（软删除或归档）
- 支持按时间、用户、操作类型筛选查询
- 审计日志写入使用异步队列，不阻塞主流程

#### Story 6: 文件管理
- **As a** 系统管理员
- **I want to** 上传和管理文件
- **So that** 我可以在系统中使用这些文件资源

**Acceptance Criteria**:
- 支持文件上传（图片、文档、压缩包等常见格式）
- 支持文件类型白名单配置
- 支持单文件大小限制配置（默认 10MB，可调整为 GB 级）
- 分片上传：单文件 > 5MB 自动分片，每片 5MB，支持断点续传
- 多线程上传：前端将分片并发上传，后端通过 upload_id 聚合分片后合并
- 支持上传进度查询：`GET /files/upload/:upload_id/progress`
- 多线程下载：后端支持 Range 请求，前端可并发下载不同分片后本地合并
- 秒传检测：基于文件 MD5/SHA256 去重，相同文件直接返回已有 URL
- 支持本地文件系统、PostgreSQL Large Object（`pg_largeobject`）、对象存储（MinIO/S3）三种后端
- PostgreSQL 模式使用 `lo`（Large Object）接口，支持流式读写和 seek，适合 GB 级文件
- 通过 `Storage` 接口抽象，配置文件切换存储后端，业务代码无需改动
- 默认使用本地文件系统，适合开发和小规模部署
- PG Large Object 模式适合无需额外服务的简单部署，文件与业务数据同库且支持事务
- OSS 模式适合生产环境大文件和高并发场景
- 返回文件的访问 URL
- 支持文件删除（软删除）

#### Story 7: 国际化和 WebSocket 实时通知
- **As a** 使用者
- **I want to** 看到实时通知和使用我习惯的语言界面
- **So that** 协作效率更高

**Acceptance Criteria**:
- 后端 API 支持 i18n 错误消息多语言（至少中/英）
- API 返回的错误消息可根据请求 Header `Accept-Language` 切换语言
- WebSocket 基于 `gorilla/websocket` 实现
- 支持系统通知的实时推送
- 支持用户维度的消息定向推送
- WebSocket 连接使用 JWT 鉴权

#### Story 8: 异步任务队列
- **As a** 系统管理员
- **I want to** 执行异步任务（如批量导入、发送邮件、数据导出）
- **So that** 耗时操作不阻塞用户操作

**Acceptance Criteria**:
- 基于 Asynq 实现任务队列
- 提供任务创建、查询、重试、取消功能
- 任务状态追踪（pending/running/completed/failed）
- 失败任务自动重试（可配置重试次数）
- 提供 Asynq Monitor Web UI 路由

#### Story 9: 开发热重载
- **As a** 后端开发者
- **I want to** 修改代码后服务自动重启
- **So that** 我不需要手动停止和重新启动服务

**Acceptance Criteria**:
- 集成 `air` 热重载工具，监听 `.go` 和模板文件变更
- 提供 `.air.toml` 配置文件，预设常用构建和监听规则
- `make dev` 或 `air` 命令一键启动热重载模式
- 修改文件保存后，服务在 1 秒内自动重启
- 构建失败时终端显示错误信息，不杀死已有进程
- 支持监听自定义目录（如 `internal/`, `cmd/`, `pkg/`）

### 2.3 Non-Goals
- 不做 SSO/SSO 单点登录集成（留给使用者按需扩展）
- 不做前端页面开发（前端完全由 React Admin 提供）
- 不做自动化部署 Pipeline（只提供 Dockerfile 和 docker-compose）
- 不做多租户（Tenant）隔离（未来版本可考虑）

#### 3.4.1 Auth Flow 详细规格

**登录 `POST /auth/login`**：

```json
// Request
{
  "username": "admin",
  "password": "password123"
}

// Response (200) — access_token 在 body，refresh_token 在 Set-Cookie
{
  "code": 0,
  "message": "success",
  "data": {
    "access_token": "eyJhbGci...",
    "expires_in": 7200,
    "user": {
      "id": "uuid",
      "username": "admin",
      "display_name": "管理员",
      "roles": ["admin"]
    }
  }
}
// Set-Cookie: refresh_token=xxx; HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth/refresh; Max-Age=604800
```

**刷新 `POST /auth/refresh`**（自动携带 Cookie 中的 refresh_token）：

```json
// Request — 无需 body，Cookie 中携带 refresh_token

// Response (200)
{
  "code": 0,
  "message": "success",
  "data": {
    "access_token": "eyJhbGci...",
    "expires_in": 7200
  }
}
// Set-Cookie: refresh_token=新值; ...  (Rotation: 旧 token 立即作废)
```

**Refresh Token 复用检测**（被撤销的 token 再次出现）：

```json
// Response (401)
{
  "code": 10403,
  "message": "Token 已被复用，所有设备已强制登出",
  "error": { "detail": "refresh_token_reuse_detected" }
}
```

**退出 `POST /auth/logout`**：

```json
// Request — Bearer token
// Response (200)
{
  "code": 0,
  "message": "success"
}
// Set-Cookie: refresh_token=; Max-Age=0  (清除 Cookie)
// Redis: 写入 access_token 黑名单 (TTL = token 剩余有效期)
```

#### 3.4.2 Redis Key 设计

| Key Pattern | Value | TTL | 说明 |
|-------------|-------|-----|------|
| `refresh:{user_id}:{token_id}` | `{user_id, device, expires_at}` | 7d | Refresh Token 状态 |
| `blacklist:access:{token_hash}` | `1` | token 剩余有效期 | Access Token 黑名单（仅注销后写入） |
| `perm:{user_id}` | `["GET:/users",...]` | 5min | 权限缓存 |
| `rate_limit:{ip}` | counter | 1min 窗口 | 限流计数 |

#### 3.6.1 文件存储后端切换

配置文件一行切换，业务代码零改动：

```yaml
# config.yaml
storage:
  driver: local          # local | pg | oss

  local:
    upload_dir: ./uploads
    public_url: http://localhost:8080/uploads

  pg:
    # PostgreSQL Large Object 模式，使用 lo_creat/lo_open/lo_read/lo_write API

  oss:
    endpoint: 127.0.0.1:9000
    access_key: minioadmin
    secret_key: minioadmin
    bucket: niko-admin
    use_ssl: false
```

**三种后端对比**：

| 后端 | 适合场景 | 优点 | 缺点 |
|------|----------|------|------|
| `local` | 开发、单机部署 | 零依赖，调试方便 | 难以水平扩展 |
| `pg` | 简单部署、GB 级文件 | 无需额外服务，事务一致性，流式读写 | 超大文件会影响 PG 性能，需手动 vacuum |
| `oss` | 生产环境、TB 级文件 | 高性能，易水平扩展，CDN 友好 | 需要额外 MinIO/S3 服务 |

#### 3.6.2 分片上传协议

**流程**：

```
Client                              Server
  │  POST /files/upload/init         │
  │  {filename, size, md5, chunks}   │
  │─────────────────────────────────►│ 创建 upload_id + Redis 记录分片状态
  │  {upload_id, chunk_size}         │
  │◄─────────────────────────────────│
  │                                   │
  │  POST /upload/:upload_id/chunk   │ ─┐
  │  chunk=0, file=blob (并发)       │  │
  │─────────────────────────────────►│  │ goroutine pool (4线程) 并发写入
  │  POST /upload/:upload_id/chunk   │  │
  │  chunk=1, file=blob (并发)       │  │
  │─────────────────────────────────►│  │
  │  ...                             │  │
  │                                   │ ─┘
  │  POST /upload/:upload_id/complete│
  │─────────────────────────────────►│ 校验 md5 → 合并分片 → 写 Storage
  │  {file_id, url}                  │
  │◄─────────────────────────────────│
```

**并发控制**：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 分片大小 | 5 MB | `storage.chunk_size` 配置 |
| 并发上传线程 | 4 | 前端 `Promise.all` 最多同时 4 个分片 |
| 后端接收线程池 | 4 | goroutine pool 限制并发写入 IO |
| 分片临时目录 | `./tmp/chunks/{upload_id}/` | 合并完成后自动清理 |
| Redis 分片状态 Key | `chunk:{upload_id}` | bitmap 标记分片上传完成情况 |
| 上传过期清理 | 24h | 超时未完成的 upload_id 自动清理临时文件 |

**断点续传**：

```
GET /files/upload/:upload_id/progress
→ { "total": 20, "uploaded": [0,1,2,5], "missing": [3,4,6..19] }
```
前端根据 `missing` 列表仅重传未完成的分片。

**秒传检测**：

```
POST /files/upload/check
{ "md5": "d41d8cd98f00b204e9800998ecf8427e" }
→ { "exists": true, "file": { "id": "...", "url": "..." } }
```
MD5 匹配则直接返回已有文件 URL，跳过上传。

#### 3.6.3 多线程下载

基于 HTTP Range 请求，前端并发下载不同分片：

```
客户端请求:
GET /files/:id/download
Range: bytes=0-5242879        (第 1 片 0-5MB)
Range: bytes=5242880-10485759  (第 2 片 5-10MB)
...（4 个并发请求）

服务端响应:
HTTP 206 Partial Content
Content-Range: bytes 0-5242879/104857600
Content-Type: application/octet-stream
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 下载分片大小 | 5 MB | 前端计算 Range 后用 `Promise.all` 并发请求 |
| 最大并发下载流 | 4 | 前端同时发起的 Range 请求数 |
| 后端并发读 | 无限流 | goroutine 天然适合并发读，无需额外限制 |

**实现要点**：
- 后端 `Storage` 接口增加 `SeekReader` 方法：`ReadAt(p []byte, off int64) (n int, err error)`
- 三种后端均支持 Range：
  - `local`: `os.File.ReadAt`
  - `pg lo`: `lo.Seek` + `lo.Read`
  - `oss`: S3 `Range` header 透传
- 合并由前端 `fetch` + `Blob` 完成后端无需感知

### 3.7 Security & Privacy

- 密码使用 bcrypt（cost=12）加密存储
- JWT Secret 通过环境变量注入，禁止硬编码
- Access Token 有效期 2 小时，Refresh Token 有效期 7 天
- API 统一经过 Rate Limiter 中间件（基于 Redis，默认 100 req/min/IP）
- 敏感接口（用户删除、角色修改）记录额外审计日志
- CORS 白名单可配置，默认仅允许前端域名
- 所有用户输入经过 validator 校验，防止 SQL 注入/XSS
- 文件上传类型白名单校验，防范恶意文件上传
- 审计日志中脱敏密码等敏感字段

#### 3.10.2 Parser: Model 解析规则

Parser 通过 Go 反射读取 Model 结构体，提取以下信息生成代码：

```go
// model/user.go
type User struct {
    ID        string    `gorm:"type:uuid;primaryKey;default:gen_random_uuid()" json:"id"`
    Username  string    `gorm:"type:varchar(64);uniqueIndex;not null" json:"username"`
    Email     string    `gorm:"type:varchar(128);uniqueIndex" json:"email"`
    Password  string    `gorm:"type:varchar(256);not null" json:"-"`
    Avatar    string    `gorm:"type:varchar(512)" json:"avatar"`
    Status    int       `gorm:"type:smallint;default:1" json:"status"`
    SortOrder int       `gorm:"default:0" json:"sort_order"`
    CreatedAt time.Time `json:"created_at"`
    UpdatedAt time.Time `json:"updated_at"`
}
```

**解析规则**：
| Model 特征 | 代码生成行为 |
|------------|-------------|
| 字段名 `ID` | 自动识别为主键，生成 `GetByID` 查询 |
| GORM tag: `uniqueIndex` | 生成按该字段的精确查询 |
| 字段类型 `string` (非 password) | 加入 List 接口的模糊搜索条件 |
| GORM tag: `json:"-"` | 该字段不暴露到 DTO（如密码字段） |
| GORM tag: `not null` | DTO 验证规则设为 required |
| 字段包含 `time.Time` | 自动加入时间范围查询参数 |
| 嵌入 `gorm.Model` 或 `DeletedAt` | 自动处理软删除过滤 |

#### 3.11.2 Makefile 设计原则

- **自文档化**：每个 target 前带 `##` 注释，`make help` 自动解析生成帮助列表
- **幂等性**：每个 target 可重复执行而不产生副作用
- **快速反馈**：`make dev` 3秒内进入热重载状态
- **跨平台**：支持 macOS（darwin）和 Linux
- **环境感知**：通过 `ENV` 变量（dev/staging/prod）切换配置

```go
// internal/config/config.go
func Load(env string) (*Config, error) {
    v := viper.New()

    // 1. 默认值 (最低优先级)
    v.SetDefault("app.port", 8080)
    v.SetDefault("db.max_open_conns", 25)

    // 2. config.yaml (按环境加载: config.dev.yaml / config.prod.yaml)
    v.SetConfigName("config." + env)
    v.SetConfigType("yaml")
    v.AddConfigPath("./configs")
    if err := v.ReadInConfig(); err != nil {
        // config.yaml 不存在不强求，纯 env 部署也合法
        log.Printf("config file not found, using env vars: %v", err)
    }

    // 3. .env 文件 (仅本地开发使用)
    v.SetConfigFile(".env")
    _ = v.MergeInConfig() // 不存在也不报错

    // 4. 环境变量 (最高优先级, 自动映射 NIKO_DB_HOST → db.host)
    v.SetEnvPrefix("NIKO")
    v.SetEnvKeyReplacer(strings.NewReplacer(".", "_"))
    v.AutomaticEnv()

    var cfg Config
    return &cfg, v.Unmarshal(&cfg)
}
```

#### 3.12.3 配置结构体

```go
type Config struct {
    App      AppConfig
    DB       DBConfig
    Redis    RedisConfig
    JWT      JWTConfig
    Storage  StorageConfig
    Log      LogConfig
    CORS     CORSConfig
    RateLimit RateLimitConfig
}

type AppConfig struct {
    Name string `mapstructure:"name"` // niko-admin
    Port int    `mapstructure:"port"` // 8080
    Env  string `mapstructure:"env"`  // dev | staging | prod
}

type DBConfig struct {
    Host         string `mapstructure:"host"`
    Port         int    `mapstructure:"port"`
    User         string `mapstructure:"user"`
    Password     string `mapstructure:"password"`
    Name         string `mapstructure:"name"`
    MaxOpenConns int    `mapstructure:"max_open_conns"` // 25
    MaxIdleConns int    `mapstructure:"max_idle_conns"` // 10
}

type JWTConfig struct {
    Secret           string `mapstructure:"secret"`            // 生产注入，不写文件
    AccessExpireSec  int    `mapstructure:"access_expire"`     // 7200
    RefreshExpireSec int    `mapstructure:"refresh_expire"`    // 604800
}

type StorageConfig struct {
    Driver     string            `mapstructure:"driver"`      // local | pg | oss
    Local      LocalStorageConfig
    OSS        OSSConfig
    ChunkSizeMB int              `mapstructure:"chunk_size"`  // 5
}
```

### 4.2 Technical Risks & Mitigations

| Risk | Impact | Probability | Mitigation |
|------|--------|-------------|------------|
| React Admin 与自定义后端 API 格式不兼容 | 高 | 中 | 提前确认 React Admin 的 REST 数据格式要求，后端 response 格式与其对齐 |
| RBAC 权限变更后缓存一致性问题 | 中 | 中 | 权限变更后主动失效 Redis 缓存；设置短 TTL 兜底 |
| WebSocket 水平扩展困难 | 中 | 低 | MVP 阶段单机部署；后续引入 Redis Pub/Sub 跨节点广播 |
| Asynq 任务队列任务丢失 | 高 | 低 | 启用 Asynq 的任务持久化；任务结果写数据库备份 |
| 代码生成器模板维护成本 | 中 | 中 | 使用 Go `text/template`，模板与代码分离，提供自定义模板能力 |
| GORM AutoMigrate 生产环境误操作 | 高 | 中 | 禁用生产环境自动迁移；强制用 `make migrate` 命令执行，迁移文件含版本号 |
| 热重载进程残留 | 低 | 中 | air 配置 `stop_on_error: true`，异常时自动清理子进程 |
| Swagger 文档与实际 API 定义漂移 | 中 | 中 | CI 中校验 `swag init` 输出无 diff；生成文件列入 gitignore，团队约定只看注解 |
| bcrypt 验证在高并发下 CPU 瓶颈 | 中 | 低 | 连接池限流 + 缓存登录成功结果跳过重复验证（失败不做缓存） |
| GORM N+1 查询性能陷阱 | 中 | 中 | 代码生成器对 `HasMany`/`BelongsTo` 关联自动插入 `Preload` 提示注释；CR 阶段必检 |
| 数据库迁移失败后状态不一致 | 高 | 低 | 每个迁移文件含 `up`（正向）和 `down`（回滚）逻辑；迁移前自动备份关键表 |
| Air Tool 未全局安装，新成员环境搭建失败 | 低 | 高 | `go install` 写入 `make init`；提供 `tools.go` 锁定依赖版本 |

## 5. Appendix

### 5.1 Frontend: React Admin Integration Notes

React Admin 前端为一个独立的 npm 项目，放在 `web/` 目录下。后端 API 需遵循以下约定以确保兼容：

- **Auth Provider**: POST `/api/v1/auth/login` 返回 `{ token, user }` 格式
- **Data Provider**: 基于 `ra-data-simple-rest` 或自定义 Provider
  - List: `GET /api/v1/{resource}?page=1&pageSize=20&sort=name&order=ASC&filter=xxx`
  - Get One: `GET /api/v1/{resource}/:id`
  - Create: `POST /api/v1/{resource}`
  - Update: `PUT /api/v1/{resource}/:id`
  - Delete: `DELETE /api/v1/{resource}/:id`
- **i18n**: React Admin 使用 `ra-i18n-polyglot`，后端返回 `message` 字段需支持多语言
